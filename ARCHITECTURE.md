# DGX Super Agent — Architecture (Cloud v1.0)

This document describes what is **built**; the live, machine-generated map is `.architecture/graph.json` (+ `graph.mmd`), regenerated by `pnpm arch`.

## 1. One core, plugins around it

```text
            user / (future) Digital Human
                        │  HTTP JSON + SSE  (Realtime/API gateway, localhost)
                        ▼
   ┌──────────── superagent/server (sa serve) ─────────────┐        superagent/ui (Web/PWA)
   │ runtime composition:                                  │◄────── React + React Flow
   │  StateStore · Verifier (+held-out) · Observatory ·    │        ("What do you want?" box,
   │  LoopEngine (+Reviewer) · Chief (+Planner) ·          │         activity feed)
   │  GoalRunner · Learning                                │
   └───────────────┬───────────────────────────────────────┘
                   │ one `dsh headless --json` process per Worker attempt,
                   │ per Chief wake, per planner/reviewer call
                   ▼
   ┌──────────── DeepSeek Harness 0.1.7-rc.2 (unmodified) ─┐
   │ profile superagent-worker = dsh-base + dsh-headless    │
   │   + @superagent/dsh-bundle (superagent_report tool)    │
   │   + browser-use + Playwright MCP (overlay patch)       │
   │ profile superagent-chief  = dsh-base + dsh-web-app     │
   │   + @superagent/dsh-bundle (superagent_* Chief tools)  │
   │ profile superagent-chief-cli = headless + bundle:      │
   │   Chief wakes (role chief), planner / reviewer         │
   │   (role planner|reviewer: read-only advisors)          │
   └────────────────────────────────────────────────────────┘
```

- **DSH is the only Agent Core** (Freeze §0.1-1). All LLM reasoning and tool use happen in DSH sessions. SuperAgent code is deterministic: state, policy, verification, observation.
- **Core modifications = 0.** DSH is an exact-pinned npm dependency (ADR-0001); we extend it only through DSH's documented seams: named profiles, `dsh plugin add` bundles, `--patch` overlays, `ctx.tools.register`, the browser-use provider seam, and `agent-default-model` / `llm-pi-ai` configuration.
- **Headless core.** The UI and future Digital Human are clients of `superagent/server`; nothing else writes orchestration state.

## 3. The Loop (Freeze §6)

```text
request ("make signup reject emails without @")
  └─ Chief.planGoal: planner (read-only DSH session, role planner) → validated plan
       (≤8 tasks, registry gate ids only, review flags) — or the deterministic one-task plan
     → goal + tasks (added as `agent`) → GoalRunner.start (durable queue, one goal per tree)

Chief.runGoal(goal) ── for each unfinished task ──► LoopEngine.runTask(task)
  loop:
    strategy = task.nextStrategy ?? first(policy.strategies)       retry-with-feedback | fresh-context | escalate-model
    model    = modelForStrategy(policy, strategy)
    Worker record + attempt n  → state executing
    snapshot git tree
    executor.run(prompt: task + scope + gates + verifier feedback + steer + approved memory)
        DSH: tool_call events → live progress reports; superagent_report tool → reports;
             final ```superagent-report``` block → result report (claim only)
    changed files = tree diff; modules = Observatory(files) ∪ reported; impact = reverse deps
    state verifying → Verifier.verify(gates) → Receipt { verdict, gateResults, workerClaim, claimOverruled, model, strategy, changed/impacted modules }
    Observatory.refresh (graph stays live)
    if PASS and task.review → Reviewer (read-only DSH session, role reviewer) reads task diff → approve | changes
    decision = loop-policy.decideNext(history):
        blocked tool calls            → Human Gate (their category, exact actions)
        protected module touched      → Human Gate (protected-module)
        Worker human_required         → Human Gate (worker-requested)   [wins over PASS]
        PASS + reviewer asks changes  → retry with the comments; persistent/unavailable → Human Gate (review-disagreement)
        verdict PASS                  → task passed → Chief wake → Learning.reflect
        attempts ≥ maxAttempts        → Human Gate (repeated-failure)
        same failure signature ×N     → next strategy, or Human Gate when exhausted
        otherwise                     → retry with feedback
```

Before the first attempt the engine pins a **task baseline**: a git snapshot commit of the whole working tree (temporary index — the user's HEAD/index are untouched; ref `refs/superagent/<task>/baseline`) and a baseline gate run recording the **named tests** that exist. Every attempt takes its own before/after snapshots.

## 3a. Verification integrity — why a Worker cannot manufacture a PASS (ADR-0011/0012)

- The verdict is a pure function of **required gate results** plus **integrity findings** (`decideVerdict`); **no required gates ⇒ FAIL**; the Worker's claim is recorded and flagged `claimOverruled`.
- **Gate Registry:** gates are human-defined (project `defaultGates` ∪ `gateRegistry`, in the store). Agent-originated tasks reference gates by id; a model-written shell command never becomes a trusted gate.
- **Integrity (blocking):** verification assets changed vs the *task* baseline (tests, runner configs, `.npmrc`/`.env`, `.superagent/`, `declared.json`, each gate's `assets`), `package.json#scripts` changed, ignored env roots (`node_modules`, venvs) changed without a lockfile change (ctime vs a marker — not forgeable with `touch`), baseline tests missing from a "passing" gate (catches `process.exit(0)` suppression), non-git project. Worker commits/resets cannot hide changes (snapshot diff). Human-granted verification changes turn a PASS into a `verification-change` Human Gate.
- **Gate processes** get an allowlisted environment (no `NODE_OPTIONS`/`NODE_TEST_CONTEXT`/npm config), parsed gates with zero executed tests fail, Playwright reports are written outside the worktree.

## 3a'. Held-out verification (ADR-0019)

A gate may carry `heldOut: { source, mountAt }`. Its tests live in `$SUPERAGENT_HOME/heldout/<source>` (registered by a human: `sa heldout add`), which the pre-tool guard forbids to every model session. At verification the Worker's final tree is exported from a snapshot commit (uncommitted and untracked files included) into a throwaway directory, `node_modules`/venvs are linked, the held-out files replace anything at `mountAt`, and the gate runs there — nothing enters the worktree. Worker feedback for a failing held-out gate carries counts and failing test *names* only (no assertions, no output). Held-out project gates always apply, even when a task names its own gates. This closes the semantic-gaming gap (special-casing the visible tests) up to the OS-user isolation residual (NEXT_STEPS P0).

## 3b. Pre-tool Human Gates (ADR-0013)

Every SuperAgent DSH session carries `ctx.tools.guard()` (bundle), DSH's monotonic deny evaluated after `tools/pre-execute` and **before execution**, for nested PTC/workflow/subagent dispatches too. `loop-policy/tool-policy.ts` classifies calls: destructive (`rm -r`, destructive git, SQL drops, disk tools), production/publication/remote hosts, privilege/credential/network expansion, obfuscated execution, direct SuperAgent API calls, reads of SuperAgent state, writes to verification assets / protected modules / outside the workspace. The engine builds each attempt's policy from trusted inputs (task baseline snapshot, store, human grants) and passes it via a file outside the worktree; an unreadable policy blocks all tools. Blocked calls become one Human Gate carrying their fingerprints; approval authorizes exactly those calls for later attempts. Independent layers: DSH's Landlock `workspace-write` sandbox (writes outside project + `/tmp` denied), the Verifier's integrity check, API credentials.

**Privileges:** anonymous (localhost reads), **agent token** (Chief tools: goals, tasks by registry id, runs; 0600 file for the Chief launcher), **human token** (register projects, resolve Human Gates, policy/model changes, human-governed learning decisions; random per server start, memory only, printed once). Worker processes never receive either token.

**Advisor sessions** (`SUPERAGENT_ROLE=planner|reviewer`): the guard allows only read tools (`read`, `glob`, `grep`, `read_image`), with SuperAgent state (including held-out tests) forbidden; no SuperAgent tools are registered.

## 3b'. Planner and Reviewer (ADR-0020)

- **Planner** (`chief-worker/src/advisor.ts`): `planPrompt` gives the request, the gate registry (ids, kind, held-out flag) and a compact architecture summary; the answer's `superagent-plan` block is validated by `parsePlan` (1–8 tasks, bounded strings, gate ids must exist — unknown ids reject the plan). Any planner failure falls back to one task carrying the whole request, with the reason recorded (`request/submitted`). Plans are added as `agent`, so the Gate Registry rule holds.
- **Reviewer:** only after gates PASS on `review: true` tasks. It receives the task's diff (task baseline → this attempt, ≤60k chars) and answers `{approve, comments}`. A rejection retries the task with the comments in the Worker prompt; `maxSameFailure` consecutive rejections, the attempt budget, or an unavailable/crashing reviewer open a `review-disagreement` Human Gate (approving it passes the task). The reviewer is never consulted on red gates and cannot turn FAIL into PASS.
- Models: policy roles `planner` and `reviewer` (fall back to `worker`), routed like Workers via `model-routes.json`.

## 3c. Chief auto-wake (ADR-0014)

`loop-policy/wake-policy.ts` classifies events: Human Gate, strategy switch (repeated failure), overruled claim, integrity violation, architecture drift / large impact, unresolved Worker blocker, goal blocked/failed and goal complete (final review) wake the Chief; learning candidates wake in low-priority batches; routine progress never does. `WakeMonitor` (persisted cursor, idempotent wake ids) → durable `wakes/` records → `ChiefDriver` (coalescing, rate limit, exponential backoff, give-up) → `DshChiefChannel`: a persistent per-project Chief DSH session (`superagent-chief-cli`, `--session-id` resumed) with the agent token and the policy's `chief` model. Pending wakes survive restarts.

## 3d. Recovery (ADR-0018)

All state is on disk. Goal runs are requested durably (`goal.runRequested`) through `GoalRunner`: one goal per project tree at a time, further requests queue, `sa serve` resumes requested goals after recovery, and approving a Human Gate resumes its blocked goal. `runTask` holds a cross-process lease; a second engine is refused. Recovery kills orphaned Worker process groups (recorded pids), closes interrupted attempts, and leaves tasks leased by another live process alone. Unparsable records raise `StateCorruptError`; a torn last line of `events.jsonl` is skipped, a torn line mid-log is an error. Stop aborts the Worker process group; Steer reaches the next attempt; re-running a goal resumes stopped tasks.

## 4. Architecture Observatory (Freeze §7)

Sources, in priority order: workspace manifests (package.json workspaces / pnpm-workspace.yaml) → declared module globs → directory fallback; dependency-cruiser import graph (+ workspace package-name mapping) → module edges tagged runtime / type-only / test-only; TypeScript AST for exported interfaces; manifests for services (bins, start scripts, DSH bundles) + `createServer().listen()` detection; git status/diff for change sets. No LLM.

File-level dependencies come from `LanguageAdapter`s (JS/TS: dependency-cruiser; Python: a static import scanner; add Tree-sitter the same way). Live reads report `freshness` and the API rescans stale graphs; the engine rescans before attributing an attempt's files. Protected modules = project ids ∪ `protected` in the baseline `declared.json` (one definition for guard and loop policy).

Outputs in `<project>/.architecture/`: `declared.json` (human-edited), `modules.json`, `dependencies.json`, `services.json`, `interfaces.json`, `dataflows.json`, `skills.json`, `drift.json`, `graph.json`, `graph.mmd`; volatile `runtime.json` and `changes.json` are gitignored.

Drift checks: runtime cycles (error), layer violations (error), `forbidden` rules (error), unregistered / missing modules (warn), edges outside a module's `dependsOn` (warn). A human can accept a specific finding via `acceptedDrift` (downgrade to warn). The `architecture-drift` gate fails a Receipt on remaining errors.

Node status: `stable`, `changing` (uncommitted change), `worker-active` (running Worker reported/edited it), `gate-failed` (latest receipt of an unfinished task failed), `protected`. Updates happen after every attempt, on `sa arch scan`, via the optional git pre-commit hook (`sa arch hook`), and via the server's file watcher.

## 4a. Learning and evolution (ADR-0015, ADR-0022)

One contract for self-improvement: kinds `memory | skill | workflow | prompt | routing-policy | verifier-policy | plugin-config`; `Candidate → Eval (arms) → Compare → Promote | Reject`. Reflection: deterministic rules + an optional DSH LLM session (`reviewer` model) whose JSON is validated and only stored as candidates. Evaluation = **fresh replay**: the task's baseline snapshot is checked out into a separate `git worktree`, a baseline arm and a candidate arm (skill/prompt/workflow injected into the prompt, or a validated policy override) run with fresh Workers through the normal loop and Verifier on harness-chosen gates; the candidate must pass with integrity intact and beat the baseline. Governance: memory human-only; skill/workflow/prompt need replay evidence; policy/config kinds need evidence **and** a human. Rejected candidates are archived with reasons; promoted skills/prompts/workflows reach later Worker prompts; promoted memory the memory section; a promoted `routing-policy` merges into the project (or global) model-policy layer; a promoted `verifier-policy` can only add protected paths / env roots / lockfiles; an invalid policy is rejected before anything is applied. `plugin-config` stays a file under `$SUPERAGENT_HOME/plugin-config/` for a human to apply.

## 4b. Model policy (ADR-0016)

Roles `chief | worker | reviewer | escalation | planner`; layers defaults ← global (`$SUPERAGENT_HOME/policy.json`) ← project record ← task pin. Un-pinned roles are resolved at every attempt, so a policy change moves queued work with no model call. Logical models map to DSH configuration through `model-routes.json` (`agent-default-model` + `llm-pi-ai` patch rows) — DSH provider management is reused, not duplicated.

## 5. Browser (Freeze §8)

- Workers: DSH browser-use seam + Playwright MCP provider (tools `mcp__playwright-mcp__browser_*`), enabled per run with `superagent/dsh-bundle/patches/worker-browser.yml` (`sa serve --browser`). Chrome DevTools MCP is available upstream but not wired.
- Verification: `e2e` gates run Playwright with the JSON reporter; `parsePlaywrightJson` turns it into pass/fail counts and failure titles inside the Receipt. The model never judges UI correctness.

## 6. State, API and events

`SUPERAGENT_HOME` (default `~/.superagent`): `projects/<id>/{project.json, goals/, tasks/, workers/, receipts/, human-gates/, reports/<worker>.jsonl, events.jsonl}`, `heldout/<project>/<gate>/` (hidden tests), `policy.json` (global model policy), `learning/{candidates,promoted,archived}/`, `skills/<name>/SKILL.md`, `runtime/workers/<id>/{prompt.md, events.jsonl, stderr.log, model.patch.yml}`, `dsh-home/` (DSH_HOME for SuperAgent profiles and sessions), optional `model-routes.json`.

API (localhost; roles anonymous/agent/human, see §3b; JSON-only POST + same-origin guard): `GET /api/policy`, `POST /api/policy` (human), `POST /api/projects/:p/policy` (human), `GET /api/projects/:p/chief`, `GET/POST /api/projects`, `GET /api/projects/:p`, `POST …/requests` (plan + run a plain-language request), `GET|POST …/chief/messages` (human ↔ Chief chat in the persistent Chief session, serialized with wakes), `GET|POST …/files` (files agents shared; `superagent_share_file`), `GET …/tree` (read-only project browser), `POST /api/links` → `GET /dl/<signed>` (15-min HMAC links for preview/download; nosniff, CSP sandbox for active types, Range), `GET …/workers/:w/transcript` (a Worker's DSH trajectory), `POST …/commands[/check]`, `GET …/commands[/:c]`, `POST …/commands/:c/stop` (human-run commands in the project; classifier-flagged ones need `confirmDanger`), `GET|POST /api/ui/appearance`, `POST /api/ui/backgrounds` (raw image/video, magic-byte checked; served via signed links), SSE `event: activity` (plain-language lines for voice/avatar clients; Digital Human embed protocol in `docs/DIGITAL_HUMAN_BACKGROUND.md`), `GET …/activity` (narrated feed), `POST …/goals`, `POST …/goals/:g/tasks`, `POST …/goals/:g/run` (start or queue), `POST …/tasks/:t/{stop,steer,model}`, `POST …/human-gates/:h`, `GET …/receipts|events|workers/:w/reports`, `GET|POST …/architecture[/scan]`, `GET/POST /api/learning…`, `GET /api/events/stream` (SSE, gap-free: consumers follow `events.jsonl` with `StateStore.tailEvents` from a cached byte offset; this is the Realtime surface a Digital Human client would subscribe to).

Operations (ADR-0023), all human-only:
- health: `GET /api/system/health`, deep `POST`;
- providers: `/api/system/providers[/probe|/test|/:name/delete]`;
- presets: `/api/system/presets[/:id/apply]`;
- project wizard: `/api/system/dirs|scan|scan/git-init`;
- backups: `/api/system/backups[/upload|/:id/restore|/:id/delete]`, downloads via signed `/dl` links;
- updates: `/api/system/update[/check|/rollback]`, `POST /api/system/restart`;
- cleanup: `/api/system/cleanup`.

Starting a goal or request runs the health preflight first. A managed install is `<base>/{source, releases/<id>, current→releases/<id>, releases.json}`, and a fresh release verifies itself at start (`verifyAfterStart`).

Remote access: a non-loopback `--host` (LAN/WireGuard) forces the token for every request; `SUPERAGENT_HUMAN_TOKEN` gives a stable human token. The UI is responsive for phones (tabs Overview · Chief · Files · Workers · Architecture · Learning · Policy · Events).

Project onboarding: with no gates given, `detectGates` proposes `unit` (npm test / node --test / pytest), `e2e` (Playwright config) and `architecture` from the repository — a human action at registration time.
